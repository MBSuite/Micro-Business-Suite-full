# Repository Audit - 2026-10-01

## Scope and Method

Read-only static review of authentication, authorization, settings, migration/schema APIs, and selected application configuration. No source code was changed. Tests, lint, and runtime behavior were not executed, so findings below are based on source inspection and should be verified with focused tests before remediation.

## Findings

### P1 - Company settings update is currently broken

`lib/settings.ts` builds one SQL placeholder per submitted field, but passes `Object.values(settings)` plus another timestamp value. The generated query only uses the submitted field placeholders and sets `updated_at` with `CURRENT_TIMESTAMP`; the extra bound value (and `id` in `values` when present) can cause PostgreSQL to reject the query due to a parameter-count mismatch. As a result, non-empty updates through `PUT /api/settings` are expected to fail rather than persist. This was not runtime-tested.

**Evidence:** `lib/settings.ts`, `app/api/settings/route.ts`.

### P1 - Settings API lacks an authorization check and interpolates request keys into SQL

`PUT /api/settings` passes the request body to `updateCompanySettings` without checking the caller's role. The route's global proxy only verifies a valid session token. The helper constructs SQL assignments by interpolating property names from the supplied object instead of validating them against a fixed column allowlist. The parameter-count defect above currently appears to prevent non-empty updates from succeeding; once corrected, the missing authorization and identifier validation must also be fixed before relying on this API.

**Evidence:** `app/api/settings/route.ts`, `lib/settings.ts`, `proxy.ts`.

### P2 - Any authenticated user can invoke a schema-changing migration

`POST /api/migrate` performs `ALTER TABLE` operations but has no in-handler authentication or admin-role check. The proxy only requires a valid session, so the route does not restrict schema changes to administrators.

**Evidence:** `app/api/migrate/route.ts`, `proxy.ts`.

### P2 - Admin access can persist after a role change

Login embeds the user's role in a JWT with a one-day lifetime. The database backup route authorizes using the role in that token rather than checking current privileges in the database. If an administrator is demoted or removed while their token remains valid, the old token may continue to satisfy the route's admin check until expiration.

**Evidence:** `app/api/login/route.ts`, `lib/auth.ts`, `app/api/admin/backup/route.ts`.

### P2 - Login logs expose unnecessary account and credential-check details

The login handler logs the attempted email, whether the user exists, and whether the password comparison succeeded. Its response also distinguishes an inactive account from invalid credentials. These details increase the impact of log access and enable account enumeration; no application-level attempt throttling is visible in this handler.

**Evidence:** `app/api/login/route.ts`.

### P3 - Authenticated users can inspect invoice schema metadata

`GET /api/db_schema` returns invoice column names and data types. It has no in-handler role check, so any valid session admitted by the proxy can obtain this metadata. This is lower impact than access to business records but is unnecessary reconnaissance surface for ordinary users.

**Evidence:** `app/api/db_schema/route.ts`, `proxy.ts`.
