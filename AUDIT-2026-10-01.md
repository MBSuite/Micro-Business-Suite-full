# Repository Audit - Reassessment 2026-10-02

## Scope and Method

Reassessment of the six findings recorded on 2026-10-01 against the current source for settings, authentication, authorization, migration, and schema APIs. The status below reflects static source inspection; no production deployment, live endpoint, or database was accessed.

The repository test command was run: `pnpm test` passed all 14 tests. The existing tests do not directly exercise the settings, admin, migration, schema, or login API routes covered by this reassessment, so passing tests do not constitute runtime verification of those controls.

## Findings and Status

### CLOSED - P1 - Company settings update parameter mismatch

The previous report described an extra-bound-parameter defect in `updateCompanySettings`. The current implementation filters submitted fields through `WRITABLE_SETTINGS_COLUMNS`, creates one value and one placeholder per accepted field, and sets `updated_at` with `CURRENT_TIMESTAMP` without an extra bound value. The reported parameter-count mismatch is no longer present in the source. Database-backed update behavior was not exercised.

**Evidence:** `lib/settings.ts`, `app/api/settings/route.ts`.

### CLOSED - P1 - Settings PUT authorization and SQL identifier validation

`PUT /api/settings` now calls `requireAdmin()` and copies only own properties named in `WRITABLE_SETTINGS_COLUMNS` before calling the update helper. SQL assignment identifiers are selected from that fixed allowlist rather than arbitrary request keys. Static source review confirms the two conditions described in the original finding have been addressed.

`GET /api/settings` intentionally remains available to any authenticated session admitted by the global session gate. It returns general company settings, with secret settings columns redacted. This is expected behavior, not an authorization finding.

**Evidence:** `app/api/settings/route.ts`, `lib/settings.ts`, `lib/auth.ts`, `proxy.ts`.

### CLOSED - P2 - Schema-changing migration authorization

`POST /api/migrate` now calls `requireAdmin()` and returns the gate's error response before running schema-changing queries when the user is not an active administrator.

**Evidence:** `app/api/migrate/route.ts`, `lib/auth.ts`.

### CLOSED - P2 - Admin access after role change

The login JWT still contains a one-day role claim, but `requireAdmin()` looks up the current user role and status in the database. The reviewed database backup route uses this gate rather than trusting the JWT role, so a stale role claim alone no longer grants access to that route. This conclusion is limited to the reviewed routes that call `requireAdmin()`.

**Evidence:** `lib/auth.ts`, `app/api/admin/backup/route.ts`.

### CLOSED - P2 - Login account enumeration and missing throttling

Unknown users, inactive accounts, and incorrect passwords receive the same `Invalid credentials` response. The handler no longer logs attempted email or password-comparison outcomes. It tracks failed attempts and applies a 15-minute lock when the count reaches 10. Expired counters are now reset before a new failure is recorded, and successful login clears the counter. Focused tests cover both behaviors.

**Evidence:** `app/api/login/route.ts`, `lib/login-throttle.mjs`, `tests/login-throttle.test.mjs`.

### CLOSED - P3 - Invoice schema metadata authorization

`GET /api/db_schema` now calls `requireAdmin()` before returning invoice column metadata.

**Evidence:** `app/api/db_schema/route.ts`, `lib/auth.ts`.

## Residual Notes

- Login throttling is held in process memory and is not shared across application instances. A shared rate-limit store is a follow-up if the application runs multiple instances.
- `GET /api/settings` access for authenticated users is intentional. Secret settings fields are redacted by the settings helper; reconsider only if the product's access policy changes.
- There are no focused tests for the reviewed settings/admin/login API controls. Add route-level tests for admin enforcement, payload filtering, and database parameter binding.
